# Пользователи, роли и безопасность

## Пользователи и роли {#users-and-roles}

Ролей две:

| Роль | Что может |
| --- | --- |
| **«Админ»** | Всё: строка управления и чипы на карточках, действия уведомлений, команды фермы, сушка AMS, режим обслуживания, экран **«Админ»**, выгрузка CSV и **«История → Действия»**. |
| **«Зритель»** | Только смотреть: «Принтеры», «AMS» и «История» («Печати», «Хронология», «Статистика»), включая графики. Кнопок, которые что-то меняют, нет; сервер отклоняет запросы администратора от зрителя. |

### Управление пользователями

Откройте **«Админ → Доступ»**:

- **«+ Пользователь»** — введите **«Логин»** (не короче 2 символов), **«Пароль»** (не меньше 8
  символов), выберите роль **«Зритель»** или **«Админ»** и нажмите **«Добавить»**.
- В строке пользователя:
    - список **роли** — выберите другую роль и подтвердите кнопкой **«Сменить»**; сеансы этого
      пользователя завершатся;
    - **«Сменить пароль»** — введите новый и нажмите **«Сохранить»**; сеансы этого пользователя
      завершатся;
    - **«Удалить»** — с подтверждением.
- Нельзя сменить собственную роль или удалить себя — так в панели всегда остаётся администратор.
- **«Последний вход»** показывает время, IP-адрес и устройство; «не входил» — пользователь ни разу
  не входил.

## Сеансы и защита входа {#sessions}

- Пароли хранятся только в виде хешей bcrypt.
- После входа браузер получает две cookie: короткий сеанс (15 минут), который продлевается
  автоматически, и cookie продления на 7 дней. Скрипты их не читают (`HttpOnly`), другие сайты их не
  отправляют (`SameSite=Strict`), и, если не задано `COOKIE_SECURE=0`, они передаются только по
  HTTPS.
- **Защита от подбора:** после 5 неверных попыток с одного адреса за 15 минут вход с этого адреса
  на время отклоняется (`Too many login attempts. Try again later.`). После 10 неверных попыток для
  одного логина за 15 минут — с любых адресов — каждая следующая попытка под этим логином ждёт перед
  проверкой пароля: 1, 2, 4, 8, 16, затем 30 секунд. Так подбор сразу со многих адресов
  замедляется. Правильный пароль после ожидания входит, поэтому запереть настоящего владельца
  нельзя; на неверный после ожидания ответ тот же — `Too many login attempts`.
- Смена роли или пароля пользователя, а также его удаление сразу завершают его сеансы.
- Сеансы подписываются ключом, который создаётся при первом запуске и хранится в `users.db`.
  Переменная `FORGE_JWT_SECRET` его заменяет; при смене ключа выходят все. См.
  [Настройки](configuration.md).

## HTTPS через nginx {#https-nginx}

Зачем:

- cookie входа передаётся в зашифрованном виде;
- уведомления браузера работают только по HTTPS;
- браузеры предлагают установить панель как приложение только с защищённого адреса.

Рекомендуемая схема: панель слушает только `127.0.0.1` (значение `WEB_HOST` по умолчанию),
`COOKIE_SECURE` остаётся `1` (по умолчанию), а перед ней стоит **nginx**, который отвечает за HTTPS.
nginx передаёт адрес посетителя в `X-Real-IP` / `X-Forwarded-For`; панель доверяет этим заголовкам
только от `127.0.0.1` / `::1`, поэтому журнал действий и ограничение входа видят настоящие адреса.
Если прокси подключается с другого адреса — Docker за nginx или Caddy на хосте, прокси на другой
машине, — укажите его в `FORGE_TRUSTED_PROXIES` (см.
[Docker за nginx или Caddy](install/docker.md#behind-nginx-or-caddy)).

В папке `deploy/` есть готовые шаблоны:

| Файл | Что это |
| --- | --- |
| `nginx-bambu.conf` | Сайт nginx: порт 80 перенаправляет на HTTPS на порту **8443**; пути к сертификату Let's Encrypt для `your-domain.example`; вход ограничен 5 попытками в минуту с адреса (запас 3, дальше `429`); всё проксируется на `127.0.0.1:58000`. |
| `setup_https.sh` | Для Raspberry Pi / Debian: ставит nginx, создаёт самоподписанный сертификат для IP компьютера в локальной сети (на 10 лет) в `/etc/ssl/bambu/`, устанавливает `nginx-bambu.conf` как сайт `bambu`, удаляет сайт nginx по умолчанию и перезапускает nginx. |
| `bambu-tunnel.service` | Обратный SSH-туннель через `autossh`: порт `58000` на публичном сервере (VPS) ведёт на порт `8000` компьютера с панелью. |

В исходном виде `nginx-bambu.conf` написан для стороны VPS (порт `58000`, сертификат Let's
Encrypt). Выберите один из двух вариантов ниже и поправьте файл.

### Вариант А: HTTPS внутри локальной сети

С помощью `setup_https.sh` и самоподписанного сертификата.

1. **До** запуска скрипта отредактируйте `deploy/nginx-bambu.conf`:
    - в обоих блоках `location` замените `proxy_pass http://127.0.0.1:58000;` на
      `proxy_pass http://127.0.0.1:8000;` (порт панели);
    - замените `ssl_certificate` на `/etc/ssl/bambu/fullchain.pem`, а `ssl_certificate_key` — на
      `/etc/ssl/bambu/privkey.pem`: эти файлы создаёт скрипт.
2. Запустите из папки проекта (IP определяется сам или указывается):

    ```bash
    sudo deploy/setup_https.sh 192.168.1.100
    ```

3. Откройте `https://<IP>:8443` — конфигурация слушает порт 8443 (порт 80 перенаправляет туда). На
   каждом устройстве один раз примите предупреждение о сертификате («Дополнительно → Перейти»), как
   объясняет сам скрипт.
4. Убедитесь, что у панели `COOKIE_SECURE=1` (уберите `COOKIE_SECURE=0`, если добавляли) и
   `WEB_HOST=127.0.0.1`, чтобы до неё можно было достучаться только через nginx.

!!! note "Примечание"
    Самоподписанному сертификату браузеры по умолчанию не доверяют. Некоторые браузеры могут не
    дать установить приложение или показывать уведомления с такого адреса; настоящий сертификат
    (вариант Б) это снимает.

### Вариант Б: доступ из интернета через VPS

Чтобы заходить на ферму снаружи, не открывая портов дома: компьютер с панелью держит SSH-туннель к
публичному серверу, а nginx на сервере отдаёт HTTPS с настоящим сертификатом.

**На компьютере с панелью:**

1. Установите `autossh` и настройте вход по SSH-ключу с этого компьютера на VPS.
2. Скопируйте `deploy/bambu-tunnel.service` в `/etc/systemd/system/`, замените `__USER__`,
   `__VPS_USER__`, `__VPS_HOST__` и `__VPS_SSH_PORT__` и включите службу:

    ```bash
    sudo systemctl daemon-reload
    sudo systemctl enable --now bambu-tunnel.service
    ```

3. Оставьте `WEB_HOST=127.0.0.1` и `COOKIE_SECURE=1`.

**На VPS:**

1. Установите nginx и положите `deploy/nginx-bambu.conf` в его сайты, заменив
   `your-domain.example` на свой домен.
2. Получите сертификат Let's Encrypt для домена. Конфигурация уже отдаёт
   `/.well-known/acme-challenge/` из `/var/www/html`, так что подходит способ *webroot*.
3. Перезагрузите nginx и откройте `https://<ваш домен>:8443`.

## Памятка по защите

Из файла проекта `SECURITY.md`. Панель управляет физическими принтерами и хранит их коды доступа,
поэтому:

- держите её на `127.0.0.1` за HTTPS-прокси или доступной только в локальной сети / VPN —
  **никогда напрямую в интернете**;
- при работе по HTTPS оставляйте `COOKIE_SECURE=1`;
- сразу смените пароль администратора, созданный при первом запуске;
- по возможности вынесите принтеры и компьютер с панелью в отдельную подсеть / VLAN.

## Как сообщить об уязвимости

Не создавайте публичный issue. На странице репозитория в GitHub используйте **Security →
Advisories → Report a vulnerability** — это закрытое сообщение, которое видят только сопровождающие.
